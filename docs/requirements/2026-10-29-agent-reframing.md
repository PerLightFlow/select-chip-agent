产品定位：面向企业研发人员的对话式助手，通过多轮追问澄清产品需求，自主安排联网芯片调研，同时支持企业项目知识的查询与维护。

## 用户已明确的目标

1. 用户用自然语言交互，Agent 通过类似 grill me 的多轮追问帮助其梳理需求。
2. Agent 按这些需求上网查询相关芯片及参数。
3. 知识库主要用于企业内部项目知识，例如项目采用的芯片、各部分由谁完成及其他项目内容。
4. 评估复用开源 Codex 的可能性，以缩短开发和部署周期；用户尚未选定运行时架构。
5. 保留现有多用户和管理员账户模式。

原有会话中确认的部署约束仍作为背景：优先 Docker；部署写入限定在 `/data/solexai/yongjun`；已允许现有 Docker 镜像和运行层复用 `/data/dockerdata`。此次只进行需求访谈和只读研究，不更改线上服务。

## 当前实现与目标的偏差

以下基于当前本地部署源码副本 `work/select-chip-agent` 的只读审查。

| 概念 | 当前实现 | 用户此次表达的目标 |
| --- | --- | --- |
| 交互 | 单次输入提取字段，返回至多三个问题；没有保存问答上下文 | 连续的需求澄清对话 |
| 芯片研究 | 先筛选本地已发布芯片，缺资料时后台抓取配置的官方目录 | 按需求联网查找和比较芯片 |

| Agent 执行 | 固定的筛选、检索、模板报告流程 | 自主安排澄清与调研，必要时回头追问，展示进度并允许停止 |

## 首版验收场景

### 场景 A：从产品想法到芯片调研

输入：“我想做一个带屏、离线运行算法的视觉检测设备，还没选芯片。”

1. Agent 结合当前回答追问影响选型的缺口，例如算法工作量、摄像头与显示接口、功耗或成本约束；不得把用户未回答的条件当作已确认事实。
2. 多轮问答沿用同一会话上下文。用户改变条件后，后续搜索和比较使用修正后的条件，指出因此变化的结论。
3. Agent 自行判断何时搜索，并可根据搜索结果再次追问；不增加强制批准需求摘要的步骤。
4. 在不依赖本地完整芯片库的情况下查找候选，优先官方来源。结果按 3–5 个候选组织参数、适配理由、风险和出处；来源不足时明确缺口，不能为凑齐数量编造候选或参数。
5. 页面呈现进度，允许停止；以 1–3 分钟交付首份可用结果为体验目标，区分首份结果与完整调研耗时。
6. 此次对话与调研结果留在个人会话。只有用户要求保存并确认的内容才进入共享知识库。

### 场景 B：查询项目芯片和分工

前置：通过已支持的文档或对话维护项目 A 的卡片，包含模块、芯片、负责人/参与人、依据和生效日期；案例数据作为测试材料，不冒充真实企业资料。

输入：“项目 A 用了什么芯片，图像采集部分是谁做的？”

1. Agent 根据项目名称、代号或别名定位企业项目；有歧义时澄清，不把不同项目合并。
2. 回答芯片、模块的负责人及参与人，关联具体依据。人员可以没有系统账号；同名人员需用部门或其他识别信息区分。
3. 默认回答当前有效记录，用户询问过去的分工或芯片时按相应历史版本回答；记录时间不能代替事实生效时间。
4. 材料不足时说明未知，来源相互冲突时展示分歧并交管理员确认，不能自动覆盖已有事实。

## 首版范围边界

首版包含连续对话、联网芯片调研、项目卡片与文档问答、确认后知识维护、既有普通用户与管理员模式。扫描件/图片 OCR 和外部企业系统自动同步后续增加；企业知识采用全员共享，不建设项目成员阅读权限。是否使用 Codex 由兼容性与维护成本验证决定，完整芯片目录也不是首版启动条件。

## 技术调查

开源 Codex 的第一轮只读调查已完成，详见 `work/codex-reuse-research.md`（相对于工作区根目录）。当前事实：

- Codex 可复用为产品的 Agent 执行层，支持会话、工具调用和交互事件；宿主应用仍负责业务上下文与业务控制。[官方说明](https://developers.openai.com/blog/codex-as-a-platform)
- 现有 Python SDK 可以控制本地 App Server，提供保留 Django 主技术栈的候选路径。[SDK 文档](https://learn.chatgpt.com/docs/codex-sdk)
- Codex 的现行模型通信要求 Responses 协议兼容。火山 Kimi 的流式工具调用和多轮上下文尚未验证。[协议兼容要求](https://learn.chatgpt.com/docs/enterprise/gateway-compatibility)
- 企业项目知识的维护、授权、来源和检索仍需在本产品中实现，不能把会话记忆视为企业项目知识库。
- 可比较“Django + Codex Python SDK/App Server”和“在现有 Django/Ark 接入上实现有限的对话与工具循环”；暂不决定是否 fork Codex。

现有 Kimi Chat Completions 已验证成功，不代表它已通过 Codex 所需协议、流式工具调用和多轮上下文兼容测试。用户已同意优先火山、按兼容成本决定是否复用 Codex，当前尚未选定运行时。

2026-10-29 的协议预检在不带鉴权的 DNS 检查阶段遇到 `Temporary failure in name resolution`，尚未发出推理请求。已核对官方字段并准备无凭据脚本 `work/probe_ark_responses.py`，记录见 `work/ark-responses-preflight.json`；实际推理请求为 0，兼容性未验证。即使之后协议预检通过，仍须单独验证真实 Codex 客户端，不将准备脚本当作兼容性完成证明。

已记录两项领域边界决策：个人会话与共享知识分离（ADR-0001），项目卡片与文档相互引用（ADR-0002）。
